## Top blockers

The 10 findings that most block **R2** (CLI-first, frontend-independent operation) and **R3** (authenticated, pinned QUIC + SSH security), ranked by severity and architectural blast radius:

1. **`AUTH-01`** (`Critical`, `R3`, `04-daemon-auth-lifecycle.md`): `RFerramHostDaemon::handle_handshake` grants an authenticated session with screen, audio, input, clipboard, file transfer, and elevation access on a bare `HandshakeMessage::ClientHello` with zero credentials, and the live client never sends `AuthRequest`.
2. **`NET-01`** (`Critical`, `R3`, `03-net.md`): `PeerCertChannelVerifier` unconditionally returns `ServerCertVerified::assertion()` and `HandshakeSignatureValid::assertion()` without verifying TLS 1.2/1.3 `CertificateVerify` signatures or checking a certificate pin, allowing active MITM certificate replay.
3. **`AUTH-02`** (`Critical`, `R3`, `04-daemon-auth-lifecycle.md`; paired with **`COM-02`** in `02-protocol-common.md`): `AuthMethod::Ed25519Signature` verifies only that the peer signed a client-chosen challenge slice with its own self-supplied public key, with no server-issued challenge nonce and no trusted-key allowlist lookup.
4. **`AUTH-03`** (`Critical`, `R3`, `04-daemon-auth-lifecycle.md`; paired with **`COM-04`** in `02-protocol-common.md`): `AuthMethod::SystemUserPassword` and in-session `AuthMethod::VaultToken` re-authentication accept any non-empty byte slice (`!credentials.is_empty()`), while initial `VaultToken` auth uses non-constant-time comparison and ignores wall-clock expiration.
5. **`COM-01`** (`Critical`, `R3`, `02-protocol-common.md`): `SecureStorage` has no OS keyring backend on Linux (`Err(NoDefaultStore)`) and encrypts local vault files (falling back to `/tmp/simply-transfer-vault`) with a deterministic, zero-entropy key `SHA-256("SimplyTransfer:NIST-SP-800-57:VaultKey:" + service_name + ":" + $USER)`.
6. **`CLI-01`** (`High`, `R2`, `08-client.md`; paired with **`UI-01`** in `09-ui-coupling.md` and **`CH-03`** in `05-channels-oob.md`): `rferram-client` has no CLI binary target, ignores `rferram-channels` (`CH-03`), and leaves session connect orchestration, VPN interface resolution, and virtual-channel routing trapped inside `rferram-ui` coupled to `cosmic::app::Task<Message>` (`UI-01`).
7. **`PROTO-01`** (`High`, `R2`, `02-protocol-common.md`; paired with **`CLI-05`** in `08-client.md`): 20 of 28 `WireMessage` leaf sub-variants lack a live production sender or handler (including `ServerHello`, `AuthRequest`, `Disconnect`, and `TopologyMessage::*`), and `ClientSessionPipeline` ignores `ServerHello` and `AuthResponse { success: false }` (`CLI-05`).
8. **`IN-01`** (`High`, `R2`, `07-media-backends.md`; alongside media stubs **`CAP-01`**, **`ENC-01`**, **`CLI-02`**, **`CLI-03`**): Linux Wayland and X11 input injectors only update in-memory fields and log `debug!`, while all platform capturers (`CAP-01`), encoders (`ENC-01`), client decode (`CLI-02`), and `wgpu` rendering (`CLI-03`) are stubs, preventing a CLI session from streaming or interacting with a host.
9. **`LIFE-06`** (`High`, `R2`, `04-daemon-auth-lifecycle.md`; paired with **`UI-02`** in `09-ui-coupling.md`): `rferram-server` accepts no CLI arguments (configured only via 3 environment variables), and `ConnectionProfile` persistence is locked to `cosmic-config` inside `rferram-ui` (`UI-02`), preventing standalone CLI configuration and profile management.
10. **`OOB-01`** (`High`, `R3`, `05-channels-oob.md`; with **`OOB-02`**, **`OOB-03`**, **`OOB-04`**, **`NET-02`**): `OobKeyIngestionManager` is dead code never bound to a socket or consulted by `handle_handshake`, falls back to a deterministic Ed25519 host key seed on vault error (`OOB-03`), starts with an empty key map (`OOB-04`), and allows arbitrary `peer_id` overwrites (`OOB-02`), while `QuicServerListener::bind` generates an unpinned ephemeral TLS cert on every start (`NET-02`).

## Contradictions

Disagreements between audit reports `01`–`10`, lead assumptions refuted by code inspection, and inline validation corrections:

1. **`rferram-client/src/render.rs` status: `01-baseline.md` ("Real") vs. `08-client.md` (`CLI-03`, "Stub")**:
   - `01-baseline.md` (`Status matrix`, line 109) characterizes `crates/rferram-client/src/render.rs:265-510` as a *"Real ... `wgpu` pipeline"*.
   - `08-client.md` (`CLI-03`, `L-CLI-3`) refutes this: `WgpuRenderPipeline` (`render.rs:218-224`) holds no `wgpu::Instance`, `Adapter`, `Device`, `Queue`, `Surface`, or `RenderPipeline`; non-test code (`:1-782`) only validates WGSL syntax and computes CPU-side plane strides/descriptors, while `wgpu::Device::create_shader_module` and `queue.write_texture` exist solely inside `#[cfg(test)]` (`:1114-1161`) with no render pass or draw call anywhere (`10-repo-packaging.md` `README claims` line 27 concurs with `CLI-03`).
2. **`WireMessage::Audio` transmission: `10-repo-packaging.md` ("neither sends nor handles") vs. `02-protocol-common.md`, `04-daemon-auth-lifecycle.md`, `07-media-backends.md` (`AUD-01`), and `08-client.md` (`CLI-07`)**:
   - `10-repo-packaging.md` (`README claims`, line 29) states that *"neither `daemon.rs` nor `rferram-client` sends or handles `WireMessage::Audio`"*.
   - `02-protocol-common.md` (`Variant coverage table`, lines 38–39), `04-daemon-auth-lifecycle.md` (`Spawned tasks`, line 87), `07-media-backends.md` (`AUD-01`), and `08-client.md` (`CLI-07`) show that `HostAudioCapturer::start_loopback_capture` (`crates/rferram-server/src/audio.rs:51-90`, spawned by `daemon.rs:203-205` and sent by `daemon.rs:630`) **does** transmit synthetic zero-filled 192-byte `AudioFrameMessage` (`HostToClientSpeaker`) packets every 20 ms, and `ClientSessionPipeline::demux_loop` (`crates/rferram-client/src/session.rs:255-272`) **does** push them into `ClientAudioBuffer` (though nothing pops them in production and `ClientToHostMicrophone` is never called on the client or handled by the server, `PROTO-01`).
3. **Server TLS certificate hash check in Ed25519 auth: `04-daemon-auth-lifecycle.md` (`AUTH-02`) vs. `serve_connection` (`daemon.rs:565-576, 720-722`) and `02-protocol-common.md` (`COM-02`)**:
   - `04-daemon-auth-lifecycle.md` (`AUTH-02`) states that `handle_handshake` (`daemon.rs:404-427`) omits comparing `credentials[32..64]` against the server's TLS certificate hash, whereas its own `Session state machine` (line 47) and `AUTH-02` body (line 120) note that the caller `serve_connection` (`daemon.rs:565-576` initial, `:720-722` in-session) *does* compare `credentials[32..64]` against `conn.peer_cert_sha256()` when `Some`.
   - Reconciled with `COM-02` (`02-protocol-common.md`), `NET-01`, and `NET-02` (`03-net.md`): because `serve_connection` checks the cert hash against the current daemon run's ephemeral certificate (`NET-02`), a captured `AuthRequest` with a client-chosen challenge (`COM-02`) is replayable against the same daemon instance until restart, and because `PeerCertChannelVerifier` skips TLS `CertificateVerify` signature checks (`NET-01`), an active MITM can replay the server's public `CertificateDer` to satisfy the channel-binding hash check without the server's private key.
