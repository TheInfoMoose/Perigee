# Phase 6 review

Range `286eafd9..e376a56e`, five files, all in `perigee-host`.

## Independent pass

### Findings

**F1. Worker that outlives the 2 s exit wait is never killed or reaped** — regression
- Where: `crates/perigee-host/src/backends/worker.rs` `wait_for_worker_exit` (timeout branch and `try_wait` error branch), called from `stop_worker` and the rejected-stdin path in `poll_seat`.
- Trigger: a capture worker that doesn't exit within `WORKER_EXIT_TIMEOUT` after its stdin closes (stopped with SIGSTOP or a debugger, stuck in D-state, wedged in libc `exit()` / atexit, or any future worker that blocks before the lifeline thread runs its callback).
- Effect: the function logs a warning and drops `Child`. `Child::drop` neither kills nor waits, so the worker keeps running as the seat user's uid, holding its Wayland connection and capture session, and becomes a zombie once it does exit. This can happen once per seat change or session stop. At launch, `stop_worker` did `child.kill()` then `child.wait()`, so the worker was always gone and reaped. The new path never sends any signal (the doc comment says so outright), so there's no fallback.
- Fix direction: keep the lifeline as the polite path, but on timeout `child.kill()` then `child.wait()`. Killing an owned, unreaped `Child` is pid-reuse safe.

**F2. `test_worker_error_reaps_worker_blocked_on_write` passes with the reaping broken** — test defect
- Where: `worker.rs` tests, `recv_timeout(Duration::from_secs(3))`.
- Trigger: remove `drop(reader)` from `stop_worker`, or reorder it after `wait_for_worker_exit`.
- Effect: the fake worker's background `echo` loop blocks on a full pipe, `sh`'s `wait` never returns, `wait_for_worker_exit` gives up at 2 s, and `capture_next_frame` still returns the repeated frame in about 2 s, inside the 3 s budget. The test goes green while the worker is leaked (this is F1's leak). It needs to assert that the worker actually exited: a budget below `WORKER_EXIT_TIMEOUT`, or checking the child pid is gone or reaped.

**F3. A failed seat poll is now swallowed and logged at warn once a second, forever** — new defect (low)
- Where: `worker.rs` `capture_next_frame`, the `if let Err(e) = self.poll_seat()` branch.
- Trigger: a persistent failure: `loginctl` missing or denied, or the worker binary path gone after an upgrade (`spawn` fails).
- Effect: at launch, the error went up the stack and ended the capture loop. Now the session stays up and shows the 64x64 placeholder indefinitely, with one `warn!` per `SEAT_POLL_INTERVAL` (1 s) and no backoff or escalation. Surviving a transient failure is reasonable. Surviving a permanent one with log spam and no signal to the client is not. Origin decided in the contract pass.

**F4. `dispatch_or_cancelled` treats a `WouldBlock` flush as success, then waits only for POLLIN** — new defect (low, unverified)
- Where: `crates/perigee-host/src/backends/wayland_shm.rs` `dispatch_or_cancelled`, the `queue.flush()` match.
- Trigger: the compositor socket's send buffer is full when `frame.capture()` is queued.
- Effect: the capture request may sit unsent while the thread polls for a reply that can't come. It stalls until cancel, or forever inside the capture worker, where nothing ever cancels. As I understand wayland-client 0.31, `blocking_dispatch` returns the flush error instead. I haven't verified that against the vendored source, and the window is narrow. Fix direction: on `WouldBlock`, also poll for POLLOUT and retry the flush.

### Checked, no finding
- `WorkerStopper::stop` vs. spawn race: a stop between `spawn` and storing the lifeline is caught by the `rejected_stdin` path. Every read result checks `is_stopped` again, the stop is sticky, and a second call returns immediately without calling loginctl (the test asserts this).
- Lifeline fd leak: `ChildStdin` comes from std's pipe, which is CLOEXEC, so later loginctl or worker spawns don't inherit it and keep the worker alive.
- Worker exit while the main thread is writing: `process::exit` runs std's cleanup, which only `try_lock`s stdout, so it can't deadlock on the main thread's held lock. Rust ignores SIGPIPE and children inherit that, so a write after the parent drops the reader gets EPIPE and the loop returns.
- `CaptureCancel`: sticky, and each `HostSessionEngine` builds its own capturer, so a cancel can't poison a later session. The eventfd is never drained, which is fine because the cancel is sticky. The poll loop handles EINTR and HUP/ERR on the Wayland fd (it reports readable, then `read` errors).
- Live-media `capture_stop` is now `Some` and wired to `HostSessionEngine::stop`. Follow-seat is unchanged in shape.
- Wire budget: the worker now fits to `RAW_FRAME_MAX_BYTES` (4 MiB) instead of 8 MiB, which matches `RawVideoEncoder` (no second rescale) and stays under the 16 MiB reader cap.
- Daemon test: tightened, not loosened. The `.ok()` that swallowed the timeout became `expect`, and `release` is set before the assertion, so a failure doesn't hang the test.
- Other new tests (`wait_readable_or_cancelled` x3, `watch_lifeline`, stop-unblocks, stop-before-first, failed poll, failed spawn) would each fail with their feature broken.
- Sensitive data: none. `testuser` and `temp_dir()` only.
- Layout: not applicable (no UI in this phase).

### Finding origins
- **F1 (worker never killed after the 2 s wait): origin plan.** 6A required "never signals... returns". That's still a regression from launch's kill+wait, and the plan's reason (no pid races) doesn't apply to killing an owned, unreaped `Child`. Kept at its severity.
- **F2 (the reap test can't fail): origin plan.** 6A set the 3 s budget, above the 2 s exit timeout, and claimed the test catches the 5R deadlock. It can't tell the deadlock from the timeout.
- **F3 (a permanent seat-poll failure only logs): origin plan.** 6B mandates a warn at every poll with no escalation. Kept low.
- **F4 (`WouldBlock` flush then POLLIN-only wait): origin coder.** Still unverified.

### F1 amendment (code evidence, written after the seal)
`packaging/linux/perigee-host.service:8,21-22` runs the host as `User=perigee` with `CapabilityBoundingSet=CAP_SETUID CAP_SETGID CAP_NET_RAW`, which has no CAP_KILL. A capture worker runs under the session user's uid, so the host can't signal it, and launch's `child.kill()` already failed with EPERM in the shipped configuration (BUG-0013's notes say the same). That makes F1 a regression only for same-uid workers (dev runs and tests), not in production. In production, launch blocked forever in `wait()`, and the 2 s timeout is strictly better. **Reclassified: new defect, low.** What's left of it is that a worker that times out is never reaped (zombie and `Child` leak), and a hung worker can't be killed. The fix direction in BUG-0021 (kill on timeout) is wrong for production. The right fix is to hand the `Child` to a reaper that calls `try_wait` later. Killing a hung cross-uid worker would need CAP_KILL, which TASK-0100's capability narrowing argues against.

## Handoff

**Verdict:** ship. Phase 6 does what it set out to do: worker stop via the stdin lifeline, seat-poll survival, a cancellable Wayland wait, a real stop test, and a single decimation. It leaves one robustness regression and one test that can't fail.

Items, by priority:
1. BUG-0022 (medium): the reap test's 3 s budget is above `WORKER_EXIT_TIMEOUT`, so it passes even with the 5R deadlock back. This is the only real guard on BUG-0013's fix.
2. BUG-0021 (low, after the amendment): a worker that times out is never reaped. Hand its `Child` to a later `try_wait` reaper. Its filed text says to kill on timeout; ignore that, because the service has no CAP_KILL.
3. BUG-0023 (low): a permanent seat-poll failure warns every second forever and serves the placeholder.
4. BUG-0024 (low, unverified): a `WouldBlock` flush followed by a POLLIN-only wait could stall a capture.

Still open: TASK-0103 (follow-seat fps and first-frame latency). 6E only removed the double decimation.
Untested: the `capture_next_frame` cancel path against a real compositor. Worth a user check: `--media live`, a static screen, then Ctrl-C.

Deferred steps to re-split: none.

Decisions for the user:
- BUG-0021: is reaping alone enough, or should a hung cross-uid worker be killable (that needs CAP_KILL)?
- For BUG-0023: end the session after N consecutive poll failures, or back off the log?
